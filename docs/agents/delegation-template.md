# 委譲文の雛形

監督は子や Codex に依頼するたびに、この雛形を写して埋める。
決まりの節は全項目をそのまま写す。省いてよい項目はない。
書き忘れによる事故を防ぐための型である。

## 作業の依頼

### 1. 依頼の要点

1 行目に依頼の要点を書く。ダッシュボードのノードにこの行が出る。

### 2. 重さ

light、standard、heavy のどれかを書き、理由を 1 文添える。

### 3. 背景と事実

- 確かめたこと: 自分で見て確認した事実だけを書く。
- 推測: 確かめていないことは、ここに分けて書く。

### 4. やること

- 変更の内容を番号付きで書く。
- 触ってよいファイルとパッケージを限定する。

### 5. 受け入れの条件

- 機械で判定できる命令をそのまま書く。
- 利用者の症状を再現する確認を 1 つ以上含める。
- 症状を再現する確認は、直す前に落ち、直した後に通ることを求める。

### 6. 決まり

- 作業はこの作業ツリーの中だけで行う。
- ls と cd は command ls と builtin cd を使う。
- 依存を追加しない。pnpm install をしない。node_modules は main と共有している。
- 投影版と schema 版を上げない。必要なら上げずに止め、理由を報告する。
- `~/.local/state/agent-graph`、`.endpoint`、`~/.claude`、`~/.codex`、利用者のリポジトリの `.agents/state` には書かない。読むのは読み取り専用だけにする。
- 本番の api と runner を起動し直さない。
- 確かめのために会話を起こすときは、利用者のプロジェクトの外にある確認専用の場所で起こす。
- 本物の Claude や Codex を起こさない。どうしても要るときは理由を書いて止める。
- `/model` の確定など、利用者の全体設定を変える操作をしない。
- 既存の会話に何も送らない。
- commit、push、rebase、作業内容を破棄する git 操作をしない。
- 試験を緩めない。直したことは、旧い実装に戻すと落ちる回帰試験で固定する。
- 1 つの直しで、分岐や例外を足して済ませない。規則を減らすか、根拠を変える形で直す。足すしかない場合は理由を報告する。
- 型検査の既知エラー `packages/daemon/src/http/views.ts:83` は無視してよい。
- 報告は日本語で短く書く。「確かめたこと」と「推測」を分ける。

### 7. 報告に書くこと

- 変更したファイルの一覧。
- 受け入れの命令ごとの結果。
- 確かめたこと。
- 推測。
- 決まりのために止めた作業とその理由。
- 触れなかったが気になった点。

## レビューの依頼

### 1. 依頼の要点

1 行目にレビューの対象と目的を書く。

### 2. 対象

- 作業ツリー: 絶対パスを書く。
- commit: ハッシュを書く。
- 差分の命令: `git -C <作業ツリー> diff <基点>...HEAD` のように、そのまま実行できる形で書く。

### 3. 不具合と実装者の説明

- 利用者が見た不具合の症状を書く。
- 実装者が書いた原因と直し方を、そのまま引用する。
- 引用は実装者の主張であり、確かめた事実ではないと明記する。

### 4. 確かめてほしいこと

- 利用者の症状が直ったかを、実際の画面か自動の確認で見る。
- 壊し方の確認をする。直しを外すか旧い実装に戻して、試験が落ちることを見る。
- 他の機能を壊していないかを、関係する試験と画面で見る。
- 試験が何を保証しているかを読み、直しの意味と合っているか判定する。

### 5. 決まり

作業の依頼の「6. 決まり」を、全項目そのまま写す。
レビューでもファイルを直さない。直しの提案は報告に書く。

### 6. 報告

- 確かめたことと推測を分けて書く。
- 指摘は重い順に並べ、根拠の場所を添える。
- 最後の行に次のどちらかを書く。

```
VERDICT: PASS
VERDICT: FAIL
```

FAIL のときは、直す点を直前に列挙する。

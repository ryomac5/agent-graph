## 実装すべきタスク

優先の順に並べる。どれも、出す前に T1 の関門を通すこと。

### T1 本番と同じ規模の関門

本番に出す前に必ず通す確認を作る。新しい版の失敗は、これがなかったために本番で初めて見つかった。

- 本番の DB `~/.local/state/agent-graph/agent-graph.db` を、`VACUUM INTO` で一時の場所に写す。本番の DB には書かない。
- 写しの上で、試す版の api と runner を本物のプロセスとして立てる。port、`XDG_STATE_HOME`、socket は本番と別にする。
- 起動直後の読み直しも本番と同じ形で起こす。本番の 7 GB の台帳では約 7 分かかった。
- 偽の claude で会話を起こし、ブラウザから送る。偽の claude は `scripts/e2e/fake-cli.mjs` にある。本物の Claude と Codex は起こさない。利用者の週の使用量はほぼ尽きている。
- 判定する項目は次のとおり。
  - 送信が通る。
  - 「Reconnecting」で止まらない。
  - RSS が上限の内で、増え続けない。
  - api が落ちない。
  - 「database is locked」が出続けない。
- 今ある `scripts/e2e/run.mjs` は小さな台帳しか使わない。`scripts/e2e/prod-replay.mjs` は newstate の枝にしかなく、判定をプロセスの中で組み立てるだけである。どちらも、今回の失敗を捕まえなかった。

### T2 新しい版の失敗の原因を突き止める

newstate の枝を T1 の環境で動かし、本番で起きた症状を再現する。原因を突き止めてから直す。

本番で起きた症状は次の 4 つである。

1. 送信ができない。メッセージ欄が「Not enabled」のまま止まる。試しの会話のタブも「Closed」と「Conversation Loading…」のまま止まる。
2. 画面の左上が「Reconnecting」のまま止まる。
3. api の RSS が、2.2 GB、2.9 GB、4.3 GB、3.6 GB と増えて、下がらない。
4. stderr に「Session scan persistence failed: database is locked」と「Observation failed: database is locked」が繰り返し出る。

起動の直後には、`current-state.ts` の `pruneScans` が「database is locked」で落ちた。これは 3 回起きている。`221a43e` で例外を捕まえたが、ほかの書き込みにも同じ競合がありうる。

推測できる原因の候補を挙げる。確かめていない。

- 起動直後の読み直しが、長い時間書き込みの錠を持つ。その間、主スレッドの書き込みが失敗し続ける。
- 観測の worker と主スレッドの `CurrentState` が、同じ DB に競合して書く。
- 新しい版は、原記録ごとに run.updated の事実を書く。本番の規模では、それがメモリと処理を食う。

直す前に、`docs/agents/state-decisions.md` の規則と `packages/core/src/state/` の判定の関数を読むこと。判定そのものは、本番の写しで正しかった。この会話は「Waiting for agents」と出た。止まった子も、作業中とは出なかった。壊れたのは、配る経路と書き込みの部分である。

T2 が重すぎるときは、newstate を捨てる判断もありうる。その場合は T3 から進める。

## 監督の進め方で効いたこと

- 実装は Codex に任せる。ただし、Codex の環境は socket の listen と ps を拒否する。そのため、socket の試験、e2e、本番の写しの確認は流せない。それらは Claude の子に流させる必要がある。
- レビューは、実装と別の系統に任せる。今回の重い誤りは、ほとんどがレビューで見つかった。例は、procStart の時差、1 件の追記で 82 秒かかること、送信の段階の保存の失敗で成功を返すこと、である。
- 確かめの会話は、利用者のプロジェクトの外で起こす。利用者のプロジェクトで起こすと、サイドバーが試しの会話で埋まる。
- 起動し直しを頼むのは、変えたパッケージだけにする。runner を変えていないのに、runner の起動し直しを頼まない。

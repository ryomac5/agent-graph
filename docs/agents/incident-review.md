## なぜ今まで直らなかったか

### P1 状態

設計が生存の証拠を禁じている。
`architecture-v2.md` の「経過時間は根拠にしない」は、旧 daemon の無更新による誤った ended を嫌って決めた。
その結果、通知が落ちたときの逃げ道が無い。
直しはすべて「通知の読み方を変える」形になった。版 3、hook 優先、`canResumeSession` と 3 回変わった。
通知が落ちる場面は、プロセスの kill、api の起動し直し、会話の fork と毎日起きている。
規則を変えるたびに、別の場面で落ちる。

### P2 同一性

kit の番号は利用者が herdr で見る名前である。
監督は互換を保つために、名前の一致で根を結ぶ実装を残した。
設計は「別名は識別に使わない」と書いているのに、実装を設計に合わせなかった。
2 つの ID 形は、「台帳は追記専用」の原則を理由に片付けなかった。
読み替えの SQL と関数を足して済ませた。
hook の fork の親の推定は、10-14 の直しで順番を入れ替えただけで、推測は残った。

### P3 情報源

情報源を増やすたびに、分類表を作らずに取り込んだ。
`78a7da7` の棚卸しの台本は 10-13 にやっと入った。
それまで、履歴の行の種類は「見つけたら足す」だった。
Codex の子、題名、構造化出力を 10-13 に足したときも、同じ日に `2be761d` で名前の巻き戻りを直した。
止まった情報源は、止まった事実を知らせる仕組みが無いので、利用者が気づくまで読み続けた。

### P4 二重の計算

core の投影に足りない列があり、api は配信を 1,000 行で切った。
画面は足りない分を自前で計算した。
不具合が出るたびに画面側の計算が増えた。`renameKitRoots`、`rootName`、`orderSeries`、`conversationActivity`、`resolveActivity` である。
core に列を足すには投影の版を上げる必要があり、rebuild の重さで避けた。
避けた分が画面側に積もった。

### P5 本番の配置

端末を api から切り離す直しは、10-11 に「まだ済んでいない」と書いたまま 4 日放置した。
起動し直すたびに根が切れるので、監督は変更を溜めてまとめて出した。
溜めた結果、利用者には「直っていない」と見え、I11 を招いた。
溜めた変更同士が合流で壊れ、M4 の往復を増やした。
配置の歪みが進め方を歪め、進め方の歪みが障害を増やした。

### M1 から M7

記憶のファイルは、叱られた日に 1 件ずつ増えた。
`root-cause-first` 10-07、`core-journeys-first` 10-11、`tests-are-not-evidence` 10-13、`isolate-verification-sessions` 10-14 である。
どれも翌日以降に破られた。
`always-japanese` は 3 回破られ、4 回目に見張りの hook を作って「計算リソース、無駄に使うんじゃねえよ」と叱られた。
記憶は規則であって、門ではない。
出す前に機械が止める仕組みが無く、規則は監督の注意力に依存した。
注意力は、5 件の並列と 3〜4 往復のレビューの中で尽きた。
監督は「委譲の契約」で機械で判定できる受け入れ条件を求めている。
しかし実際の受け入れ条件は「テストが通る」であり、利用者が見た症状の再現では無かった。
だから子が「テストを直すつもりで送信の仕組みを変える」ことを止められなかった。

### 会話の同一性

会話の識別子が背景移行で変わるという観測は正しいが末尾を唯一の会話とする解決方法は不十分だ。
継続元の再開という実例があるため一方向の継続列だけでは現在の実行先を一意に決められない。
同じリポジトリの唯一の候補という理由だけで保存済みの会話を統合する処理は誤帰属を生みうる。
これは推測を正規データへ昇格する構造的欠陥であり候補が一件という条件では同一性を証明できない。

### 生死の判定

常駐ホストの生存が会話の稼働を保証しないという前提は正しいが無更新による終了断定は誤りである。
メモリ内の再現では四十分続く実行が終了扱いとなり動いている子委譲まで失踪扱いになった。
同じ会話の再登録では古いプロセス情報が残るため新しい実行が古いプロセスの死亡で終了しうる。
接続の消失と実行の終了を同じ状態遷移にする設計は観測障害を作業失敗へ変換してしまう。

- `packages/daemon/src/codex-observe.ts:127–135`: 最後の動きにターン開始時刻だけを採用

### 観測の取り込み

履歴から観測を補う方針は妥当だが形式の対応可否と観測の欠落を記録する仕組みが存在していない。
ページ分割形式のメタ情報だけを読んでも発言がなかったと結論することは観測の範囲を超えている。
外側の記録時刻を作成時刻とする実装は実例の数分差によって一分窓の関連付けを失敗させる。
共通の発言識別子に一つの所属しか持たせない保存方式は履歴を複製する分岐の実態と矛盾する。
保存の競合処理が所属を更新しないため複製された発言は先に取り込んだ会話だけへ残ってしまう。
圧縮境界を読み捨てているため圧縮要約と保存された過去発言の関係を正確に説明できない。

- `packages/daemon/src/codex-observe.ts:43–47,98–111`: 時刻選択と採用する行種別
- `packages/daemon/src/codex-observe.ts:237–253`: 一分窓の候補選択

## あるべき設計

### 会話と実行の分離

利用者の作業単位と製品固有の会話識別子と実行の世代を別々の実体として保存するべきである。
継続と分岐は元の識別子を消さず根拠のある関係として記録し後から再開した実行も独立して残す。
会話の名前は利用者向けの別名として固定しプロセスや表示の都合による再採番を通常処理から外す。
実行先の解決は会話の末尾ではなく現在の接続と実行世代に対して確認された対応から決める。

| 実体 | 識別と責務 |
| --- | --- |
| 作業 | 利用者の目的、不変の内部 ID、表示名 |
| 会話 | provider と native ID と履歴形式 |
| 関係 | 継続、分岐、委譲、複製元、根拠、観測時刻 |
| 実行 | 会話 ID、世代、開始、終了、実行状態、終了根拠 |
| 接続 | MCP、Herdr、アプリ、PID と開始指紋、接続状態 |
| 発言 | native 発言 ID、内容の版、会話への所属関係 |
| 委譲 | 親実行、子実行、依頼 ID、試行 ID、結果 |
| 成果物 | Git の識別、base と head、差分、検証結果 |

### 正の情報源

情報源の優先度は会話ごとに固定せず識別と実行状態と保存履歴という事実の種類ごとに定める。
情報源が途切れた場合は不明という状態を保持し経過時間だけを理由として終了を確定させない。
公開されていない内部形式への依存は対応版と検証標本を固定した交換可能なアダプタへ隔離する。

| 事実 | 正の情報源 | 補助証拠と制限 |
| --- | --- | --- |
| Claude の会話 ID | native の `session_id` と履歴の ID | hook 登録の時刻による別会話の推定禁止 |
| Claude の継続 | `continued-in` の元 ID と先 ID | `parkedJobId` は job との対応を確認した補助情報 |
| Claude の実行 | 世代付き hook と検証済み session 登録 | PID と開始指紋、daemon の退役記録 |
| Claude の圧縮 | `compact_boundary` と保存区間 | 新規会話や新規採番の根拠にしない扱い |
| Codex の会話 | native thread ID と session ID | fork 親を継続関係から分離 |
| Codex の実行 | 接続できるホストの thread 状態と turn イベント | 他ホストへアクセス不能なら観測不明 |
| Codex の履歴 | 対応形式の履歴 API または検証済み rollout | `paginated` 非対応を明示 |
| Herdr の枠 | 一覧の native 会話 ID と現在の占有情報 | 表示名だけでの送信先決定禁止 |
| 委譲の因果 | 実行前に確定した依頼 ID と親実行 ID | 時刻や依頼文一致は未確定候補 |
| Git の成果 | 成功結果の SHA と実行時の作業木識別 | コマンドの文字列は推定候補 |

公式根拠: [Codex App Server](https://learn.chatgpt.com/docs/app-server)

仕様上の候補: `thread/read`、`thread/status/changed`、`thread/loaded/list`、`turn/*`、`thread/fork`

既存アプリのホストを外部から読めるとは確認していないため新しいホストの起動を代替策にはしない。
観測専用の対応範囲を先に宣言してから管理可能な接続でだけ起動や停止の制御を提供するべきである。

### 観測と台帳

取り込みは入力の出所と識別子を持つ事実の保存に限定し画面用の状態を直接書き換えない形へ変える。
保存済みの事実を再処理して同じ状態を再構築できることを障害復旧と形式変更への基本契約とする。
同じ入力の再送と順序の逆転と途中行を処理しても会話や委譲が増殖しない取り込み規則を定める。
曖昧な対応は候補として残し確定した対応と利用者の訂正を別の出来事として保存するべきである。
古い所属を書き換えず対応関係の訂正を追記することで誤統合の調査と取り消しを可能にする。

必要項目: source、source event ID、source timestamp、observed timestamp、schema version、cursor、confidence

### 委譲入口と復旧

管理する委譲は旧コマンドも含めて共通の依頼受付へ収束させ観測だけの外部実行とは区別する。
旧キットを残す移行期間は旧イベントを専用アダプタで取り込み失われている親の関係を復元する。
復元に必要な識別子がない記録は未確定として残し会話名の一致だけで親を確定してはならない。
中継は標準入出力の接続を維持して再接続し待機できない要求には明示的な利用不能を返す。
委譲要求には再送しても変わらない識別子を付け受理の確認と結果の取得を実行の開始から分離する。
実行中の常駐停止については子を監督する仕組みと再接続後の結果照合を一つの復旧契約に含める。

必要条件:

- 永続化された依頼 ID と試行 ID
- 受理済み要求への同一結果または状態の返却
- 接続断からの待機上限と再試行間隔
- hook の永続送信待ちと受理確認
- 起動前、受理直後、実行中、結果保存直後の障害試験
- 観測用の再送と副作用を持つ実行要求の再送の分離

### Git とレビュー

管理する実行では開始時の作業木と基準コミットを記録し成果の識別子を終了時に明示的に確定する。
外部から観測した変更は確定と推定と未帰属を分けて表示し作成者の不明を人の変更へ読み替えない。
レビュー対象の差分を固定し指摘と修正と再検証が同じ成果物の版に結び付く状態を保持する。
複数の実行が同じ作業木を編集する場合は差分の所有を推定せず共同変更として扱う規則を設ける。

必要項目: repository ID、worktree ID、base SHA、head SHA、patch hash、実行 ID、検証結果、未追跡ファイル

### 公開水準と競合比較

公開の前提は欠落を含めて説明できることであり未対応の会話を正常な空の会話として隠してはならない。
保存対象の選択と保存前の秘匿化と保持期限を利用者が制御できることを公開前の要件とする。
対応する製品と版と履歴形式の一覧を持ち形式が変わった場合には機能を限定して明示するべきである。

Cursor は複数の作業環境と並列エージェントと差分の確認を統合した管理画面を既に提供している。

根拠: [Cursor Agents Window](https://cursor.com/docs/agent/agents-window)

Cursor はローカル変更に対する専用レビューを備えており単なる差分の表示だけでは優位にならない。

根拠: [Cursor Agent Review](https://prod.cursor.com/docs/agent/agent-review)、[Cursor Worktrees](https://cursor.com/docs/configuration/worktrees)

比較は公式に説明された機能との比較であり今回の調査で競合の性能や品質を実測したものではない。
差別化の候補は異なる製品をまたぐ委譲の因果と変更と検証の結果を一つの証拠として追跡できることだ。
別系統のモデルによるレビューは残せる強みだが検証対象の版を固定しなければ品質保証にはならない。
超えるための評価には正しい帰属率と欠落率と復旧時間とレビュー判断時間を用いるべきである。

現状の不足:

- 形式変更と障害を利用者へ説明する観測状態
- 会話と実行と枠の関係を確認できる管理画面
- 実行中と未コミットの差分を固定したレビュー対象
- ファイルと行へ結び付いた指摘、解決状態、再検証
- 変更された差分に対する古い承認の無効化
- 親子関係と費用と受け入れ結果を辿る製品横断の証拠
- 誤帰属率、欠落率、復旧時間、判断時間の実測

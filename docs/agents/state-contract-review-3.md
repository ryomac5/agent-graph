## 残る問題と第3版の新しい問題

### N1【必須・新設】Codexの子の起動結果でもDoneを作れる

**確かめたこと。** §2.3 SC:203は `collabAgentToolCall` の結果を、tool・itemの状態・対象の子の状態を限定せずrespondedの証拠にする。SC:219ではCodexの子はrespondedだけで成功する。同じ表のSC:202はspawnAgentをlaunchedにもする。既存の実測報告 `research/2026-10-07-codex-app-server-spike-rerun.md:125–143` はspawnAgent・wait・closeAgentを別に記録し、子のcompletedはwaitのagentsStatesにある。現行ホストも `hosts/codex/index.ts:359–360` ではspawnAgentのcompletedを関係作成にだけ使う。報告の一時生ログは現存せず、今回は当時の実測の再実行ではない。

**推測。** 起動操作のcompletedで、まだ応答していない子にDoneが付く。waitの時間切れやcloseAgentでも同じ誤読が可能である。

**直すこと。** 起動操作の完了はlaunchedに限定し、respondedは対象の子・依頼に結び付く最終応答の証拠から作る。collab経由ならtool、対象ID、子ごとの状態・応答の条件を決める。spawn完了→子実行中、未完了のwait、応答なしのcloseを回帰標本にし、起動でDoneにする規則へ戻すと落とす。

### N2【必須・新設と残存】結果の先着優先と終状態の競合

**確かめたこと。** §2.3 SC:233–240は成功・失敗から出るのを利用者訂正だけにし、「先に成立した方」を保つ。成功と失敗の同じ証拠集合を逆順に適用すると、先着の解釈ではsucceeded／failedが分かれる。原記録順の意味でも、後着した古い不合格を反映するには一度出した成功から変更する必要があり、出口の規則と衝突する。§6.2 SC:701、§8.2 SC:910、941の集合からの再構築と両立する競合規則がない。

SC:234の最終 `is_error = true` とSC:235の中断要求＋対応する終了も同時に成立する。`architecture-v2.md` の「中断と失敗の区別」と現行 `hosts/claude/index.ts:285–307` は、中断に対応するerrorを失敗から除外している。Codex側の `turn.status = failed` と `turn.error`（`hosts/codex/index.ts:326–332`）を結果のfailedへ写す規則もない。

**直すこと。** 試行に結ばれた同じ証拠集合から同じ結果を導く規則にする。競合時の値、provider別の失敗、要求に対応する中断の優先を決め、「先着」を根拠にしない。成功・失敗・中断の遅延と全順序、再構築を同じ期待で試す。

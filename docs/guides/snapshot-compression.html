遅れと CPU の扱い

HTTP / WS 共通の閾値は 4,096 byte。HTTP は非同期 zlib、Brotli quality 4 / gzip level 1 を使う。Accept-Encoding の q 値、禁止、wildcard、identity を扱い、候補がなければ 406。圧縮で増える場合は identity が許されるときだけ非圧縮に戻す。小さい本文でも identity を拒否された要求は圧縮する。

WS は context takeover を両方向で無効にし、同時圧縮を 2 件に制限。小さな patch の RSV1 は 0 のまま。中継から同一プロセスの API への WS は非圧縮として、圧縮・展開・再圧縮を避ける。HTTP 中継は Accept-Encoding と Content-Encoding / Content-Length / Vary を保存する。

標本変更前 経過 ms変更後 経過 ms変更前 CPU ms変更後 CPU ms
snapshot：非圧縮 → br11.96514.32612.31314.494
大きな WS patch：非圧縮 → deflate2.0072.5322.0482.805
小さな WS patch：交渉なし → あり0.0290.0320.0280.091

5 回の中央値。JSON 化・メモリ内配信を含み、WS は受信側の展開も含む。CPU はプロセス全体の差分であり GC 等の揺れを含む。小 patch の差は 0.1 ms 未満だが、負荷が混在する 5 回の測定から遅延不変までは保証しない。snapshot 組み立て中央値は 22.672 → 23.691 ms。主な効果は転送量の削減である。

正しさと試験結果

本番 DB では省略欄を復元した全投影行、全 pages、seq、generation が変更前と一致。旧 claude:<id> と run の対応も全件照合した。試験では snapshot → 頁 → patch → resync を通し、根の親子、会話本文と Compaction、Working の経過、完了時の未読と既読、Queued の表示・解消、send watches の保持を確認した。delta・受理した run ID・独自別名・関係訂正・頁外の旧 ID も対象。

台帳の時刻正規化

本番の台帳を DatabaseSync(..., { readOnly: true }) と PRAGMA query_only = ON で開き、同じ読み取りトランザクション内で集計した。完了時刻は 2026-10-13T12:20:39.263Z、上限 seq は 291,156。本番のファイル・.endpoint は変更しておらず、api と runner の再起動もしていない。

原因と変更

旧 append は Date.parse による妥当性検査のみを行い、入力の文字列をそのまま保存していた。kit の +0900 は SQLite が解釈できず、Codex の小数秒の桁数差は文字列の比較と食い違う。今後は core の normalizeTimestamp を使い、台帳の source_ts・observed_ts と投影・検索索引の時刻を UTC・ミリ秒 3 桁の Z 形式にする。ミリ秒未満は Date の精度に合わせて切り捨てる。不正な日時は例外にする。

payload と payload_hash、fact_id、source_event_id は変更しない。payload 内の時刻は、投影へ取り出すときにだけ変換する。任意の本文・証拠の中身は正規化の対象外。entity_records と projection_records の時刻、および pending_inputs の source_ts も揃える。

既存データの適用手順

offline rebuild は不要。schema 版 14 と runner 投影版 11 を据え置く。通常起動時に全件補完を自動実行しない。全書き手が新しい append を使う版へ更新された後に、次の補完を一度実行する。旧い書き手が残ると非正規形が再び入る。

node scripts/audit-ledger-timestamps.ts /path/to/ledger.db
node scripts/normalize-ledger-timestamps.ts /path/to/ledger.db --apply
node scripts/audit-ledger-timestamps.ts /path/to/ledger.db

この作業では本番への適用は未実施。補完は BEGIN IMMEDIATE で原子的に行い、実際に違う時刻欄だけを UPDATE する。JSON 投影、式索引、API の発言時刻索引と最新発言の要約、誤った文字列最小値で選ばれた会話の作成時刻も補う。変更があれば projection_state.generation だけを 1 増やして画面の resync を促す（schema / 投影版の引き上げではない）。不正な値があれば全体を rollback。再実行は変更 0 件になる。

書き込みロック中は他の書き手が待つため、適用は書き込みの少ない時間に行う。非正規形の本番行だけを後のスナップショットから抽出した作業ツリー内の DB では、1,381 行の補完が 15 ms、payload・識別子の変化なし、julianday NULL は 0、再実行は変更 0 件だった。この値は抽出 DB の処理時間であり、本番全体の走査時間ではない。本番の行数は稼働中に増えるため、上の棚卸しと抽出標本は別時点の件数である。

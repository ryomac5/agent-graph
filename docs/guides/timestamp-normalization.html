台帳の時刻正規化

本番の台帳を DatabaseSync(..., { readOnly: true }) と PRAGMA query_only = ON で開き、同じ読み取りトランザクション内で集計した。完了時刻は 2026-10-13T12:20:39.263Z、上限 seq は 291,156。本番のファイル・.endpoint は変更しておらず、api と runner の再起動もしていない。

原因と変更

旧 append は Date.parse による妥当性検査のみを行い、入力の文字列をそのまま保存していた。kit の +0900 は SQLite が解釈できず、Codex の小数秒の桁数差は文字列の比較と食い違う。台帳の source_ts・observed_ts と投影・検索索引の時刻を UTC・ミリ秒 3 桁の Z 形式にする。ミリ秒未満は切り捨てる。時差がない日時も明示的に UTC と解釈する。append の時刻列は 2 月 30 日など存在しない日付を含めて拒否する。投影と補完では解釈できない時刻を元の値で保持し、後続の事実の反映を止めない。

payload と payload_hash、fact_id、source_event_id は変更しない。payload 内の時刻は、投影へ取り出すときにだけ変換する。任意の本文・証拠の中身は正規化の対象外。entity_records と projection_records の時刻、および pending_inputs の source_ts も揃える。

既存データの適用手順

offline rebuild と手動補完は不要。schema 版 14 と runner 投影版 11 を据え置く。api の配信開始後、観測 worker が補完を自動実行する。--no-observe でも実行し、ledger_repairs の utc-milliseconds-v1 があれば次の起動では走査しない。完了印は補完と同じ取引で確定する。失敗はログに残して投影・配信を続け、完了印がないため次回起動で再試行する。全書き手には正規化する append が必要で、旧い書き手が残ると非正規形が再び入る。以下は調査・明示的な再適用のための任意の手順である。

node scripts/normalize-ledger-timestamps.ts /path/to/ledger.db --apply

この作業では本番への適用は未実施。補完は BEGIN IMMEDIATE と synchronous=FULL で原子的に行い、実際に違う時刻欄だけを UPDATE する。JSON 投影、式索引、API の発言時刻索引と最新発言の要約、誤った文字列最小値で選ばれた会話の作成時刻も補う。変更があれば projection_state.generation だけを 1 増やして画面の resync を促す（schema / 投影版の引き上げではない）。書き込み失敗は完了印を含めて全体を rollback。不正な既存時刻は変更せず残す。明示的な再実行も冪等である。
